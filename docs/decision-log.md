# Decision log

Every design decision behind this experiment, with the reasoning and the alternatives that were rejected.
Written as the decisions were taken, not reconstructed afterwards. D-01 was committed before any code existed,
which is what makes the predictions in it a pre-registration rather than a summary.

## D-01 · 2026-09-11 · The design: one job, thirty-eight times, four loop designs

- **Alternatives:** (a) run experiment 5/6's held-out design again on more claims tasks — the ceiling is structural, not a sampling problem, and another run of it would answer nothing new; (b) keep the six claims tasks and add more conventions per task — six different jobs, each exercising a different handful of conventions, is exactly what made the learning curve unreadable, and more conventions per task deepens the confound rather than removing it; (c) one repeated job but with *numeric bands* as the hidden knowledge (the v1 design) — a band has to be estimated from hundreds of entangled examples, so thirty cases would have produced a null result whichever loop design won; (d) an LLM as the senior underwriter in the ask-a-senior arm — cheaper to write, but then the arm measures the senior's model as much as the apprentice's loop, and a bad answer is unattributable. The senior is deterministic code.
- **Why the revamp:** the claims experiment failed for one structural reason. A learning curve needs **the same job repeated**; six different jobs, each with its own handful of conventions, gives six one-shot trials in a trench coat. Experiment 7 gives one job — rate a life-insurance application — thirty-eight times, against a body of unwritten practice deep enough that thirty cases do not exhaust it. The declining error curve is the validation. If the memory designs do not bend down, the honest finding is that these loops do not capture house knowledge, and that is what gets published.
- **What carried over, unchanged in shape:** the LangGraph `StateGraph` with `interrupt()` / `Command(resume=)` and `SqliteSaver`; the manual-mode request/response file protocol and the pause-print-resume runner (`src/run_experiment.py`); the raw-log memory store (`src/feedback_memory.py` → `src/underwriting/memory.py`); the freeze-manifest-plus-SHA approach; `scripts/archive_run.py` (extended with `--uw-run-id`, additively); the per-run summariser; and the stateless operator agent pattern. New package `src/underwriting/`, new config `config/underwriting.yaml`, new frozen data under `data/underwriting/`, new artifacts under `artifacts/uw/<run_id>/`, new tests under `tests/underwriting/`. **Nothing in the claims experiment's behaviour or tests changed.**
- **The five arms** differ in one thing each: `new_joiner` (manual only, keeps nothing), `notebook` (every past markup verbatim, newest first; appends the markup as written), `written_rules` (its own rule book; a reflection call rewrites the whole book each training case), `precedent` (the three nearest past cases with their correct answers; files this one afterwards), `ask_senior` (may ask up to four questions of a deterministic oracle; keeps nothing).
- **The metric.** Rating distance in ladder steps — Pref+ 0 … Decline 8 — with postpone off the ladder at a fixed 2 when exactly one side postpones and 0 when both do. Also per case: decision exact match, modifier F1 with the flat-extra band included, driver recall.
- **Tiers are derived, never assigned.** Two engines: `rate_manual_only` (a careful reader of the manual alone) and `rate_house` (the golden). A rule **fires** when switching it off alone changes the scored answer — decision, rating class, modifiers or drivers. Zero fired = clean, one = judgement, two or three = compound. The generator injects the attributes a target rule needs, runs both engines, and throws the draw away unless the derived fired set matches exactly.
- **Deviations, all of them:**
  1. **Operators are Claude Fable 5.1 (`model: fable`), not Haiku** — the lead's instruction on 2026-09-11.
  2. **The written-rules arm is shown the whole rule book**, not the entries whose trigger matches. The book is at most twenty-five entries; a retrieval step would confound "did the memory carry the rule" with "did retrieval find it", which is not the question this arm asks.
  3. **Reflection is one extra call per training case, for `written_rules` only.** Notebook and precedent update automatically. Live call count: 38 + 38 + 68 + 38 + 76 = **258**, not the design's ~400.
  4. **The training mix is 9 clean / 13 judgement / 8 compound, not 9 / 14 / 7.** The build brief's section 5 asks for both that mix *and* every rule firing in at least three training cases in at least two shapes. Those are arithmetically incompatible: twelve rules at three firings each needs 36 firings, and 14 judgement cases (one firing each) plus 7 compound cases (at most three each) supply at most 35. Moving one case from judgement to compound is the smallest change that satisfies the set — 13 + 24 = 37 firings against 36 needed — and every other section-5 constraint holds as written, including the sliding-window mix (every ten consecutive training cases: 2–4 clean, 4–5 judgement, 2–3 compound) and case 1 not being clean. The design's stated shares move from 30 / 45 / 25 to 30 / 43 / 27.
  5. **The precedent store is `artifacts/uw/<run>/precedent/filed_cases.jsonl`, not `precedent/cases.jsonl`.** The brief names both that file and the per-arm run log `<arm>/cases.jsonl`; for the arm called `precedent` they are the same path. The run log keeps the brief's name.
  6. **A markup may contain the token `A1c`.** The brief allows digits in a markup only for the case id and the class names; `A1c` names a laboratory test, not a threshold or a point value, and the alternative was renaming the test. `src/underwriting/markup.py::forbidden_digits` encodes exactly these three allowances, and a test runs it over every markup the generator can produce.
  7. **The stub smoke is archived alongside a full 30 + 8 stub pass** (logs only, no transcript, no checkpoints). Six training cases cannot show a learning curve — every rule that fires in cases 1–6 fires there for the first time — so the six-case smoke proves the machinery and the full pass proves the arms separate at all. Both are labelled stub everywhere they appear.
  8. **LangGraph checkpoints under `artifacts/uw/*/checkpoints/` are git-ignored**, matching the existing rule for `logs/checkpoints/`. They are rebuilt by the runner and ran to 22 MB for the full stub pass.
- **Predictions, restated before the run** (mean rating distance in ladder steps, trailing five-case mean): new_joiner flat and jagged, ~1.8 throughout, ~1.9 held-out; notebook 1.8 → 0.6, 0.8 held-out; written_rules the same finish from a slower start; precedent 1.8 → 0.9, 1.1 held-out, good on repeats and weak on the novel; ask_senior 1.3 → 1.2, helping at once, never improving, paying every case. **A measured floor to set against those numbers:** the mean ladder distance between `rate_manual_only` and the golden is **0.933** over the thirty training cases and **0.875** over the eight held-out ones (0.000 clean, 1.154 judgement, 1.625 compound). That is the most any memory can recover; a live operator sits above it because it also misreads bands. The design's 1.8 is a prediction about Fable's total error, not about this floor.
- **Validation checks, registered in advance and computed by `scripts/summarize_uw_run.py`:** (1) cases 1–3 must be a dead heat for the four non-asking arms — they hold identical information there, and a difference beyond sampling noise means something has leaked and the run is void; (2) the clean tier must stay flat for everyone — experience should not change performance on cases the manual already covers; (3) the two held-out cases firing a rule that never appeared in training should be missed by every arm that cannot ask. All three pass on the stub smoke and on the full stub pass.
- **The leakage rule and how it is enforced.** The operator never sees house-rule text or ids, point values of hidden rules, tier labels, golden answers, or any statement of what it is measured on. `src/underwriting/audit.py` checks every request file for forbidden keys, rule ids, tier words used as values, the case's own golden or markup, any rule statement, and any numeric token that appears in a rule statement and nowhere in the manual — that last set is computed, not listed by hand. Two exemptions: the ask-a-senior answers (quoting a rule is that arm) and the operator's own rule book (its prose, not ours). `python -m src.underwriting.run audit --run-id <id>` runs it over a whole run; the archived smoke reports 0.
- **Impact:** new `src/underwriting/` (sixteen modules), `config/underwriting.yaml`, `data/underwriting/` (freeze `d95f49f1f930…`), `scripts/summarize_uw_run.py`, `.claude/agents/underwriter-operator.md`, an addendum to `docs/OPERATOR_PROTOCOL.md`, a README section, and `archive/experiment-7_stub_smoke/`. `scripts/archive_run.py` gains `--uw-run-id` and `--logs-only`; `.gitignore` gains one line. **119 new tests** (313 passed, from 194). The one failing test in the suite, `tests/test_graph_routes.py::test_run_config_reads_the_current_experiment_yaml`, is pre-existing and belongs to experiment 6: it asserts `config/experiment.yaml` holds run_009's phase-1 settings while the committed file holds run_010's phase-2 settings. Nothing in experiment 7 touches it.

## D-02 · 2026-09-12 · uw_001 finishes on Opus 5 after the Fable quota was exhausted mid-run

- **What happened.** The live run `uw_001` was orchestrated with **Claude Fable 5.1** operators (D-01, deviation 1), one fresh stateless subagent per request file. Over 2026-09-11/12 the run was interrupted five times by subscription session limits and resumed each time from disk without loss. At 14:42 on 2026-09-12, with **167 case records already written and 37 operator calls still owed**, the account's Fable quota was exhausted outright: every spawn returned `HTTP 429 — You've reached your Fable limit. Switch to another model to continue.` Three orchestrator rounds and a direct two-operator test by the lead confirmed it was a standing quota, not a burst.
- **The state at the cut.** `new_joiner`, `notebook` and `precedent` were **complete on Fable operators** — 30 training cases and 8 held-out cases each, 38 responses apiece. `written_rules` stood at 27 of 30 training cases with the held-out phase not started (14 calls owed); `ask_senior` at 26 of 30 with the held-out phase not started (23 calls owed).
- **Alternatives:** (a) **pause until the Fable quota reset** — the only option that keeps all five arms on identical operators, at the cost of an unknown wait; (b) **finish the 37 calls on Opus 5** and record the deviation; (c) **publish three complete arms** and drop `written_rules` and `ask_senior` as incomplete. The lead chose **(b)** on 2026-09-12, having been shown the confound in (b) and the loss in (c) before deciding.
- **The confound, stated plainly.** The two arms that finish on Opus 5 are the two the headline rests on: at the cut, `written_rules` led the memory arms on training error and `ask_senior` was at zero error across 24 cases. Opus 5 is the stronger model, and it produces their last training cases **and the whole of their held-out test**, which is the comparison the article turns on. Their held-out numbers are therefore **not** a like-for-like comparison against the three Fable arms and must never be reported as one. What survives the switch intact: the three Fable arms compared against each other; all five arms' training curves up to case 26; and the two validation checks that live in the early cases (the cases 1–3 dead heat and the flat clean tier), all of which were computed on Fable-only records.
- **How the switch is made visible rather than described.** `config/underwriting.yaml` now carries `model_identifier: claude-opus-5` above a comment giving the date, the reason and this decision number. The identifier is stamped into **every case record at the moment it is written** (`nodes.py` → `cases.jsonl`), so `artifacts/uw/uw_001/<arm>/cases.jsonl` reports, per case, which model produced it; the 167 records written before the switch keep `claude-fable-5-1`. No record was rewritten. A reader can partition the run by model without taking this entry's word for it.
- **What did not change:** the frozen data pack (`d95f49f1f930…`), the cases, the goldens, the house rules, the manual, the scorer, the markup, the senior oracle, the arm mechanics, the operator prompt template and the blind-operator definition. Only the model behind the subagent changed, and only for the last 37 calls.
- **Housekeeping recorded here rather than left to be rediscovered.** The pre-existing failure noted at the end of D-01, `tests/test_graph_routes.py::test_run_config_reads_the_current_experiment_yaml`, was fixed on 2026-09-11 (commit `a85d012`): it asserted experiment 6's phase-1 settings while `config/experiment.yaml` holds the phase-2 (run_013) settings, so the assertions were pointed at the committed configuration. The suite is green.

## D-03 · 2026-09-12 · The ask-a-senior arm is excluded from the published analysis

- **What it measured, and why that is not what it was meant to measure.** The fifth arm keeps no memory but may ask up to four questions before deciding, answered by `src/underwriting/senior.py` — deterministic keyword routing over the frozen house rules. In `uw_001` it scored **0.000 ladder steps on all 38 files**, 121 questions asked, every decision exactly right. That is not a finding about escalation as a loop design; it is a finding about the oracle. The senior always knew the answer, including the two rules held back for the held-out test, so the arm measures "what if a perfect lookup sat next to the apprentice" rather than "what if a colleague did". A real senior is an experienced average — the manual, somewhat more practice, and their own blind spots.
- **The manual made it worse, not better.** The starter manual's *"refer to underwriting judgement"* lines were written as honest gap markers (D-01). They double as a map: they tell an asker exactly which lines to ask about, so four questions were enough to cover every rule a file could fire. The combination of a signposted manual and an omniscient senior makes a perfect score close to inevitable, which the pre-registered prediction of 1.3 badly missed.
- **Decision, taken by the lead on reading the result:** drop the arm from the article and from all three figures. The article says in one bullet that it was built, what it scored, and why that says more about my senior than about the design — silence would be worse than a short honest note.
- **Nothing is deleted.** The arm's code, its 76 request/response files, its 38 case records and its question counts stay in the repo and in `artifacts/uw/uw_001/ask_senior/`. `scripts/summarize_uw_run.py` still reports it. Only `articles/underwriting-apprentice/assets/make_figures.py` excludes it, via a module-level `ARM_ORDER` constant rather than by filtering at each call site.
- **Consequence for the model-switch caveat (D-02).** With ask-a-senior gone, `written_rules` is the only published arm touched by the switch: its last two training files and all eight held-out files ran on Opus 5. `new_joiner`, `notebook` and `precedent` are Fable end to end, so the clean three-way comparison — 0.88 against 0.25 and 0.38 on unseen work — carries the article's main claim, and the written-rules held-out number is reported as indicative. Both figures and the article state this.
- **The next version of this arm**, if it is built: a senior that holds the manual plus a *subset* of the house rules, answers from that subset only, and says "I don't know, use your judgement" outside it — with the subset frozen in advance and reported. That measures escalation against a colleague instead of against an answer key.

## D-04 · 2026-09-12 · The published curve is a cumulative average over all 38 files

- **What changed.** The article's main figure was a trailing five-case mean over the 30 training files, with the held-out phase shown only as a separate bar chart. It is now the **running (cumulative) average of rating error over every file done so far, across all 38 files**, with files 31–38 shaded as the held-out phase on the same axes.
- **Why.** The trailing window on a metric whose per-file values are almost all 0, 1 or 2 moves in steps of 0.2 and crosses constantly; the written-rules line spent several windows above the new joiner's purely on window composition, which reads as "the design with a rule book is worse here" and is an artifact rather than a fact. The running average answers the question a manager actually asks — across everything this person has touched, how far off have they been — and it is monotone enough to read at a glance. **No smoothing, interpolation or fitting is applied**: the plotted value at file n is exactly the mean of files 1..n, and `scripts/summarize_uw_run.py` still prints the pre-registered trailing-five series unchanged.
- **What the change bought, substantively.** Showing the held-out files on the same axes makes the key contrast visible as a direction rather than a table: when the feedback stops, the new joiner's running average **turns up** (0.667 → 0.711) while all three memory designs keep falling (0.400 → 0.368, 0.333 → 0.316, 0.467 → 0.447).
- **Pre-registration status.** D-01 registered the metric (ladder distance) and the validation checks, and named the trailing-five mean as the *presentation*. The metric, the data and the checks are untouched; only the presentation changed, after the results were seen. That sequence is recorded here so a reader can weigh it.
